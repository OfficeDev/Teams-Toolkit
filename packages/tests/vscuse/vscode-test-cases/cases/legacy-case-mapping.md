# Generated-to-Legacy Case Mapping

This mapping relates each YAML-authored case to its generated plan and the legacy VScUse plan it
replaced. It is the migration record for plans that are gone: the legacy plan column names a file
that no longer exists wherever the status is **Full**.

## Status

- **Full**: the generated case covers the legacy scenario intent with semantic steps and file
  checks, and the legacy plan has been removed.
- **Partial**: the generated case covers the legacy scaffold and lifecycle but stops short of part of
  the legacy flow, such as its chat validation or its negative input path, so the legacy plan is kept
  until that gap closes.

A generated case is still **Full** when it sends the legacy prompt and asserts an error-free reply
where the legacy plan asserted reply wording. The wording is the model's, so asserting it would tie
the case to a service this repository does not control; the legacy grounding keywords such as
`Contoso Electronics`, `Northwind Health`, and `Oil change` are that wording. The rest of the legacy
chat assertion, that no `error` appears in the reply, is asserted verbatim.

The Teams Agent with Data OpenAI cases assert no grounded answer, and are still **Full**, because
no legacy OpenAI plan asserted one either: all ten ran on a fake OpenAI key. Those templates also
hardcode `gpt-3.5-turbo`, and `text-embedding-ada-002` for Azure AI Search, in the generated project,
so even a real key redirected to an Azure OpenAI resource resolves a deployment that resource does
not host. The two Node Azure AI Search cases keep the fake key and assert the error reply their
legacy plans asserted. The rest assert that the agent replied, which is what their legacy plans
asserted, except that four Python plans asserted the resulting `Error code: 401` in the terminal,
which no adapter reaches. `compile-vscuse-case-bundles.md` records this under VCB-113 and VCB-114
and carries the follow-up for tightening these checks once the templates move to a current model.

## Legacy Azure AI Search Plans Not Mapped

The nine Azure AI Search remote Teams and Agents Playground plans remain recorded. Their shared
setup writes Azure AI Search and embedding credentials to `env/.env.dev.user` or
`env/.env.playground.user`. The current `localEnvironment` operation mutates only the runtime file
written by `m365agents.local.yml`, and `localUserEnvironment` intentionally targets only
`env/.env.local.user`, so composing either operation would produce a plan whose remote or
Playground runtime is missing credentials. Full replacement requires an explicit environment-file
operation rather than treating the local mutation as portable across targets.

## Legacy Tab Flows Not Mapped

The three tab cases deliberately drop the negative input flows the legacy plans recorded, so those
legacy plans stay in place:

- `Basic_Tab_Local_Debug.json` types `g#ed!-k?/h` and a thirty-three character name into the app name
  box to read back the validation messages. A scaffold operation authors one answer per prompted
  question, so it has no way to author a rejected answer followed by a corrected one.
- `Basic_Tab_Remote_Debug.json` invokes provision before signing in to read the resulting "needs a
  Microsoft 365 account" message. The semantic compiler rejects that ordering at compile time
  (`VCB_PROVISION_PREREQUISITE`), which is the contract rather than a recordable runtime flow.
- `Basic_Tab_Remote_Debug.json` also dismisses leftover notifications before provisioning. That is
  environment noise rather than product behavior and has no semantic operation.
